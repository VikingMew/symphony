# Documentation Alignment Matrix

This matrix records claim-level ownership: each long-lived topic has exactly one owning
document (single source of truth); other documents link instead of restating. It is the review
checklist for keeping product direction, architecture, and operator docs
consistent. `mix docs.check` enforces document structure; this matrix tracks claim ownership.

## Canonical Topics

| Topic | Canonical current doc | Current truth |
| --- | --- | --- |
| Runtime configuration source | `README.md`, `docs/user-guide.zh-CN.md`, `docs/persistence_and_auth.md`, `docs/long_term_direction.zh-CN.md` | One current PostgreSQL workflow per project is durable authority. Cold start and successful mutations atomically publish one in-memory per-project/source snapshot; normal runtime reads never query PostgreSQL. The auto-created Default project is only the empty-table bootstrap placeholder; once another project exists, runtime reads require explicit project context and never select Default or the first project. Prompt rendering and rate-limit evaluation retain the issue/run project context. Background refresh is single-flight, generation-guarded, and last-known-good. Split YAML files remain import/export artifacts, not runtime fallback. |

The quality gate runs before writes. Description-size limits combine defaults with deterministic normalized-label overrides; exceeding either limit adds one non-blocking milestone advisory. Successful completion writes one persisted measurement event after Linear mutations. Uncorrected quality-gate runs reuse the existing no-progress streak and persistent `BlockingDecision` path. |

Codex includes the returned URL and completion proof in the final Linear completion request. Control-plane reconciliation moves a `Ready to Merge` issue to persistent `Blocked` only when that exact open PR has a definitive merge conflict. Human review/merge and Linear's merged-PR automation own `Ready to Merge -> Done`; Symphony has no backend merge route. |

Production Panel startup reads packaged migrations and PostgreSQL `schema_migrations` before business children, performs no DDL, and fails closed on pending, unknown-applied, or unreadable state. A started Panel reports `checks.migrations: "current"`; the database-free execution-worker is unaffected and the local CLI retains automatic migration. |

| Deployment and image ownership | `docs/compose.md`, `README.md`, `docs/deployment.md`, `docs/execution-worker-operations.md` | Root Compose runs PostgreSQL, migration, and Panel services plus an opt-in trusted HTTP execution worker profile. `docs/compose.md` owns the rule that migration, Panel, and execution worker have no engine CLI/socket, privileged mode, daemon, nested Compose, or container-management surface. Root Compose defaults to a centralized `symphony:local` Panel that combines control and local execution, contains Codex, and mounts `codex_home`. Its published-image override selects worker mode and pulls a Codex-free, control-only Panel built with `SYMPHONY_EMBED_CODEX=false`; the override removes the Panel's Codex credential mount. The separate execution-worker image always contains Codex and owns OAuth state in `execution_worker_codex`. Shared Docker stages pin Codex CLI `0.150.1`, mise `2025.8.16`, Erlang `28`, and Elixir `1.19.5-otp-28` for Codex-capable targets; mutable tool caches stay in existing writable workspace/cache volumes under read-only roots. The runtime images jointly own token-free system Git configuration: GitHub HTTPS authentication uses `gh auth git-credential`, and GitHub SCP-style SSH URLs rewrite to plain HTTPS. Fresh workspace volumes need no credential seeding or external Git/SSH host-key configuration; service bootstrap and PR handoff retain GitHub token environment while Codex children do not. GitHub Actions owns variant smoke, execution-worker `make all`, image build, and amd64/arm64 publication; implementation agents own only static/source validation and never invoke a container engine. Host operators own Compose deployment operations, including health verification followed by explicit listening enablement through the public Orchestrator API after restart. Panel and worker are non-root, least-capability, separately stored/networked; the worker cannot join the database network. Runtime proxy env vars, trusted forwarded headers, health/readiness probes, and reverse-proxy/Kubernetes examples remain supported. Public TLS/domain termination and production worker egress filtering remain external edge infrastructure. |

SQLite is a stopped backup import source only. Default tests are database-free; the explicit PostgreSQL smoke owns migration/import/concurrent-write evidence. |

## Documentation Update Requirements

When implementation changes product behavior, update the docs in the same change:

- Runtime/config behavior: `README.md`, `docs/user-guide.zh-CN.md`, `docs/persistence_and_auth.md`, `docs/long_term_direction.zh-CN.md`.
- Settings behavior: `docs/user-guide.zh-CN.md` and this matrix.
- Worker/deployment behavior: `README.md`, `ARCHITECTURE.md`, `docs/worker-panel-decoupling-design.md`, and deployment docs.
- Observability behavior: `README.md`, `ARCHITECTURE.md`, `docs/long_term_direction.zh-CN.md`, and run/events docs when present.
- Public repository positioning: root `README.md`.

Future intent belongs in an L3 design with an explicit status. Current behavior belongs in its
canonical owner and should link to reviewable implementation where delivery evidence is useful.
